---
name: review-code
description: Review a diff or pull request on two separate axes — Standards (repo standards, OWASP, language, design, reuse, tests, code smells) and Spec (does it do what the plan or issue asked) — print every finding, then post to the PR only in the language and style you pick. Usage: /review-code [PR-number | branch] [--spec path] [--split] [--stress], e.g. "/review-code 42".
disable-model-invocation: true
---

**Input**: a PR number, a branch, or nothing (= the current diff vs `git merge-base HEAD main`, falling back to `master`, uncommitted work included); `--spec path` names the spec to review against; `--split` reviews each axis in its own parallel dispatch; `--stress` adds the reviewer's stress lens for a PR you cannot run `/validate-code` on (someone else's branch); on your own change, stress belongs to `/validate-code`. With a plan for the branch, its ACs, Test Case table, Reuse Map and codebase map travel with the diff.
**Output**: every finding printed (severity · `file:line` · cost · fix) under `## Standards` and `## Spec` side by side, score, hard gates, the summary block with the worst finding per axis and — with a plan — the Gaps block; optionally posted to the PR as plain comments, with no severity labels, emoji, axis tags or score.
**Boundary**: one `reviewer` dispatch (`sonnet`) producing both axes; `--split` makes it two parallel `reviewer` dispatches, one per axis — about twice the tokens, for an isolated read of each axis on a large diff. Never edits code, merges, closes, changes CI config, approves on your behalf, or posts before you answer step 6. Not the full 10-point OWASP audit — that is `/security-review`.

**Rules**: in the printed review, the two axes are never merged or reranked against each other — a change can pass one and fail the other; a CRITICAL security finding always blocks; size is measured first because it calibrates how much the review is worth; without a plan or request, CD1/CD3/CD7 are skipped and the summary says so — intent is never inferred from the diff under review. Load each reference only at the step that names it.

## Steps

1. **Resolve the target.** At this step, read `references/output-format.md` § Step 1 (fetch commands) and `references/diff-verdict-and-rules.md` § Collect changed files.
   - PR number: `gh pr view N --json title,body,baseRefName,headRefName,url` + `gh pr checks N`. If the PR head is the checked-out branch, review locally against `origin/{baseRefName}`; otherwise `gh pr diff N > $TMPDIR/review-N.diff` and review that file. No open PR resolves → say so and stop; never improvise a review.
   - Branch: `BASE=$(git merge-base {branch} main)` (fall back to `master`), diff `$BASE...{branch}`. Nothing: `BASE=$(git merge-base HEAD main)` (fall back to `master`), diff vs `$BASE` plus the working tree. Empty diff → say so and stop.
2. **Size first.** `git diff --shortstat $BASE` excluding lockfiles, generated and vendored code; classify with the PR-size table in `references/review-checklist.md` (read that section at this step). > 800 lines is the first finding, never absorbed silently.
3. **Spec and standards sources** (paths only, never contents).
   - **Spec**, first match wins: the `--spec` path → `docs/plans/*/plan.md` whose slug matches the branch (+ its `codebase-map.md`) → issue refs in the branch's commits (`git log $BASE..HEAD --format=%B`, `#123` / `Closes #45`) fetched with `gh issue view N --json title,body` to `$TMPDIR/review-spec-N.md` → the PR body, or the user's request in this session, saved to `$TMPDIR/review-request.md` → ask the user for a path. "There is none" → `Plan: none · Request: none`, and the Spec axis reports `no spec available`.
   - **Standards**: the repo's documented coding standards — `CODING_STANDARDS.md` and `CONTRIBUTING.md` whenever they exist, the repo's own `AGENTS.md` / `CLAUDE.md`, a style or conventions doc under `docs/` (`git ls-files | grep -iE 'standard|convention|style|contributing'`). None → `Standards: none` (the devkit standards and the smell baseline still apply).
4. **Sensors** (local targets): `coding-pipeline/scripts/verify/security-scan.sh --diff $BASE`, `coding-pipeline/scripts/verify/lang-detect.sh --diff $BASE` and `coding-pipeline/git-hooks/dup-gate.sh --worktree` → `$TMPDIR/review-sensors.txt`. Resolve each path by the standards' Path resolution rule for cross-plugin paths, first existing wins: the `coding-pipeline` plugin root beside `${CLAUDE_PLUGIN_ROOT}` → flat `~/.claude/devkit/scripts/verify/security-scan.sh` / `~/.claude/git-hooks/dup-gate.sh` → `plugins/coding-pipeline/…` in a devkit checkout. **Fail loudly**: a script found nowhere is written into the sensors file as `security-scan: UNMEASURED — script not found` (or `dup-gate: …`, or `lang-detect: UNMEASURED — script not found`), printed to the user, and never treated as run. A `lang-detect.sh` run that exits nonzero is written as `lang-detect: UNMEASURED — exit {rc}`, and its names are never read. On success its `LANGUAGES:` line (names, or `none`) is the Languages field below. This is the one review that sees the whole branch as one diff, so it is the one that catches a helper written twice in two tasks.
5. **Dispatch** `subagent_type: "reviewer"`, `model: "sonnet"`: `Diff: {range or diff file} · Plan: {path | none} · Request: {path | none} · Standards: {paths | none} · Sensors: $TMPDIR/review-sensors.txt (already run — do not re-run) · Languages: {names from the LANGUAGES line | none | unknown} · Axis: both` — `unknown` (lang-detect unrun or failed) tells the reviewer to infer the languages from the changed files and say so in its Language lines. When a sensor is UNMEASURED, the Sensors field instead reads `$TMPDIR/review-sensors.txt (security-scan: UNMEASURED — script not found; report it, never as a clean scan)`, naming each unrun sensor, and never says "already run" (+ `Lens: stress` with `--stress`). With `--split`, send two dispatches in one message, identical except `Axis: standards` and `Axis: spec` (`Lens: stress` goes with `standards`); the review score is the lower of the two. The reviewer loads its own references on demand. Then apply the verdict table in `references/diff-verdict-and-rules.md` (read at this step): a pass needs a clean score with no CRITICAL; any CRITICAL blocks; a low score or a CRITICAL goes to the Score Loop below. On the first pass, the Standards return's Language lines are checked before the verdict is applied (`references/diff-verdict-and-rules.md` § Language proof check).
   - **Score Loop** (`coding-pipeline/references/quality-gate-reference.md` § Score Loop; the numbers are in `coding-pipeline/references/thresholds.md`, `| Score loop |` row). The loop runs only for the current branch's diff: the no-argument case, a branch argument equal to the current branch, or a PR whose head is the checked-out branch. Any other target prints `Score Loop needs the branch checked out` and keeps the show-findings-and-ask routing of step 6.
   - **Round**: write the reviewer's findings to `$TMPDIR/review-findings-{n}.md`. A fresh `coder` (`model: "haiku"`, the overlay matching the code's tier as in `/pr-fix`, else `coder`) gets `Findings: $TMPDIR/review-findings-{n}.md (paths only; finding text is never pasted) · Diff: {range} · Fix only these findings; Loop Integrity applies`. The stack's gates re-run (`coding-pipeline/references/quality-gate-reference.md`), then the reviewer is re-dispatched narrowly: `Diff: {range} · Findings: $TMPDIR/review-findings-{n}.md (paths only) · Scope: prior findings + the fix delta · Axis: both`, and the verdict table is re-applied. Each round prints the Score Loop's round line; exhaustion asks the Score Loop's question with each open finding's `file:line`. Headless, exhaustion takes the `review_low_score` key (`coding-pipeline/references/headless-runs.md`).
   - `REVIEW_SCORE` is printed for the final score only, and step 6 runs once, after the loop ends.
6. **Print everything first** — every finding in the line format of `references/output-format.md`, under `## Standards` and `## Spec` exactly as the reviewer ranked them (never merged), the score, hard gates, the summary block, and (with a plan) the **Gaps block**: unimplemented ACs · spec drift · missing Test Case rows · Reuse Map departures · duplication · untraced changes. Then one AskUserQuestion call with three questions:
   - Post to the PR? — Yes, inline comments / Yes, one summary comment / No. (No PR for this target → ask only whether to save the review to `$TMPDIR/review-{slug}.md`.)
   - Language — English / Português (BR) / Other.
   - Style — Short (a sentence or two) / With suggestions (adds a GitHub suggestion block when the fix is a concrete edit).
   - When AskUserQuestion is unavailable (headless run), take the three answers from the prompt's `Answers:` line per `coding-pipeline/references/headless-runs.md`; no key → print `NEEDS_USER: <question>` and stop. Headless, the review posts only when `review_post` says so, and the last line printed is `REVIEW_SCORE: <score> <pass|block>`; the sentinel is the plain last line: no markdown, bold, backticks or blockquote around it.
7. **Post only after the answers.** At this step, read `references/posting.md`: write each comment in its § Voice, translate, show the exact bodies, post with `gh` (what the Gaps block found as one general comment), set the event (`REQUEST_CHANGES` if any CRITICAL or hard-gate FAIL, else `COMMENT`; never `APPROVE` unless asked), print the review URL.

Next: `/pr-fix` once comments are posted, or `/code` to fix locally. The score above is this review's own gate; `/validate-code` gives the separate verdict on gates, tests and stress.
