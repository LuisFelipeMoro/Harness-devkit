---
name: review-code
description: Review a diff or pull request on two separate axes — Standards (repo standards, OWASP, language, design, reuse, tests, code smells) and Spec (does it do what the plan or issue asked) — print every finding, then post to the PR only in the language and style you pick. Usage: /review-code [PR-number | branch] [--spec path] [--split] [--stress], e.g. "/review-code 42".
disable-model-invocation: true
---

**Input**: a PR number, a branch, or nothing (= the current diff vs `git merge-base HEAD main`, falling back to `master`, uncommitted work included); `--spec path` names the spec to review against; `--split` reviews each axis in its own parallel dispatch; `--stress` adds the reviewer's stress lens for a PR you cannot run `/validate-code` on (someone else's branch); on your own change, stress belongs to `/validate-code`. With a plan for the branch, its ACs, Test Case table, Reuse Map and codebase map travel with the diff.
**Output**: every finding printed (severity · `file:line` · cost · fix) under `## Standards` and `## Spec` side by side, score, hard gates, the summary block with the worst finding per axis and — with a plan — the Gaps block; optionally the same posted to the PR.
**Boundary**: one `reviewer` dispatch (`sonnet`) producing both axes; `--split` makes it two parallel `reviewer` dispatches, one per axis — about twice the tokens, for an isolated read of each axis on a large diff. Never edits code, merges, closes, changes CI config, approves on your behalf, or posts before you answer step 6. Not the full 10-point OWASP audit — that is `/security-review`.

**Rules**: the two axes are never merged or reranked against each other — a change can pass one and fail the other; a CRITICAL security finding always blocks; size is measured first because it calibrates how much the review is worth; without a plan or request, CD1/CD3/CD7 are skipped and the summary says so — intent is never inferred from the diff under review. Load each reference only at the step that names it.

## Steps

1. **Resolve the target.** At this step, read `references/output-format.md` § Step 1 (fetch commands) and `references/diff-verdict-and-rules.md` § Collect changed files.
   - PR number: `gh pr view N --json title,body,baseRefName,headRefName,url` + `gh pr checks N`. If the PR head is the checked-out branch, review locally against `origin/{baseRefName}`; otherwise `gh pr diff N > $TMPDIR/review-N.diff` and review that file. No open PR resolves → say so and stop; never improvise a review.
   - Branch: `BASE=$(git merge-base {branch} main)` (fall back to `master`), diff `$BASE...{branch}`. Nothing: `BASE=$(git merge-base HEAD main)` (fall back to `master`), diff vs `$BASE` plus the working tree. Empty diff → say so and stop.
2. **Size first.** `git diff --shortstat $BASE` excluding lockfiles, generated and vendored code; classify with the PR-size table in `references/review-checklist.md` (read that section at this step). > 800 lines is the first finding, never absorbed silently.
3. **Spec and standards sources** (paths only, never contents).
   - **Spec**, first match wins: the `--spec` path → `docs/plans/*/plan.md` whose slug matches the branch (+ its `codebase-map.md`) → issue refs in the branch's commits (`git log $BASE..HEAD --format=%B`, `#123` / `Closes #45`) fetched with `gh issue view N --json title,body` to `$TMPDIR/review-spec-N.md` → the PR body, or the user's request in this session, saved to `$TMPDIR/review-request.md` → ask the user for a path. "There is none" → `Plan: none · Request: none`, and the Spec axis reports `no spec available`.
   - **Standards**: the repo's documented coding standards — `CODING_STANDARDS.md` and `CONTRIBUTING.md` whenever they exist, the repo's own `AGENTS.md` / `CLAUDE.md`, a style or conventions doc under `docs/` (`git ls-files | grep -iE 'standard|convention|style|contributing'`). None → `Standards: none` (the devkit standards and the smell baseline still apply).
4. **Sensors** (local targets): `coding-pipeline/scripts/verify/security-scan.sh --diff $BASE` and `coding-pipeline/git-hooks/dup-gate.sh --worktree` → `$TMPDIR/review-sensors.txt`. Resolve each path by the standards' Path resolution rule for cross-plugin paths, first existing wins: the `coding-pipeline` plugin root beside `${CLAUDE_PLUGIN_ROOT}` → flat `~/.claude/devkit/scripts/verify/security-scan.sh` / `~/.claude/git-hooks/dup-gate.sh` → `plugins/coding-pipeline/…` in a devkit checkout. **Fail loudly**: a script found nowhere is written into the sensors file as `security-scan: UNMEASURED — script not found` (or `dup-gate: …`), printed to the user, and never treated as run. This is the one review that sees the whole branch as one diff, so it is the one that catches a helper written twice in two tasks.
5. **Dispatch** `subagent_type: "reviewer"`, `model: "sonnet"`: `Diff: {range or diff file} · Plan: {path | none} · Request: {path | none} · Standards: {paths | none} · Sensors: $TMPDIR/review-sensors.txt (already run — do not re-run) · Axis: both` — when a sensor is UNMEASURED, the Sensors field instead reads `$TMPDIR/review-sensors.txt (security-scan: UNMEASURED — script not found; report it, never as a clean scan)`, naming each unrun sensor, and never says "already run" (+ `Lens: stress` with `--stress`). With `--split`, send two dispatches in one message, identical except `Axis: standards` and `Axis: spec` (`Lens: stress` goes with `standards`); the review score is the lower of the two. The reviewer loads its own references on demand. Then apply the verdict table in `references/diff-verdict-and-rules.md` (read at this step): ≥ 8.0 with no CRITICAL passes; any CRITICAL blocks; below 8.0 surfaces the findings for a decision.
6. **Print everything first** — every finding in the line format of `references/output-format.md`, under `## Standards` and `## Spec` exactly as the reviewer ranked them (never merged), the score, hard gates, the summary block, and (with a plan) the **Gaps block**: unimplemented ACs · spec drift · missing Test Case rows · Reuse Map departures · duplication · untraced changes. Then one AskUserQuestion call with three questions:
   - Post to the PR? — Yes, inline comments / Yes, one summary comment / No. (No PR for this target → ask only whether to save the review to `$TMPDIR/review-{slug}.md`.)
   - Language — English / Português (BR) / Other.
   - Style — Terse (one line per finding) / Detailed (with suggestion blocks) / Conventional Comments.
7. **Post only after the answers.** At this step, read `references/posting.md`: translate and format, show the exact bodies, post with `gh` (the Gaps block as one general comment), set the event (`REQUEST_CHANGES` if any CRITICAL or hard-gate FAIL, else `COMMENT`; never `APPROVE` unless asked), print the review URL.

Next: `/pr-fix` once comments are posted, or `/code` to fix locally. The score above is this review's own gate; `/validate-code` gives the separate verdict on gates, tests and stress.
